GUIDE RAVALINK · RC1

Exploitation et dépannage

Sécurisez l’accès réseau, vérifiez l’API, résolvez les problèmes et consultez les limites de la RC1.

Réseau et sécurité

  • TCP 2333 : API REST Lavalink v4 et WebSocket. N'ouvrez que ce port si vos clients doivent joindre le nœud.
  • Sortie réseau : nécessaire pour GitHub Releases, les fournisseurs audio et les connexions vocales Discord.
  • Authentification : toutes les requêtes REST et la connexion WebSocket doivent fournir le secret dans l'en-tête Authorization.
  • TLS : placez un reverse proxy HTTPS/WSS devant RavaLink lorsque le trafic traverse Internet. Le proxy doit transmettre les connexions WebSocket (Upgrade).
  • Prometheus : les métriques sont désactivées par défaut. L'endpoint n'ajoute pas d'authentification ; ne le rendez pas public sans contrôle d'accès.
  • Privilèges : utilisez un utilisateur système non-root pour l'installation native ; le conteneur officiel s'exécute sans privilèges root.

Exemple Nginx (reverse proxy WebSocket)

Remplacez audio.example.com par votre nom de domaine et configurez votre certificat TLS dans le bloc serveur :

server {
    listen 443 ssl http2;
    server_name audio.example.com;

    # ssl_certificate et ssl_certificate_key à configurer

    location / {
        proxy_pass http://127.0.0.1:2333;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}

Ne retirez pas l'authentification RavaLink au niveau du proxy. Si vous utilisez un proxy TCP ou un tunnel, vérifiez qu'il préserve les connexions WebSocket et les en-têtes HTTP.

Vérifier le fonctionnement

Depuis la machine qui héberge le nœud, vérifiez d'abord que le processus écoute sur le bon port. Les routes protégées nécessitent l'en-tête Authorization.

curl -i -H "Authorization: VOTRE_MOT_DE_PASSE" \
  http://127.0.0.1:2333/version

# Exemple pour une route authentifiée :
curl -i -H "Authorization: VOTRE_MOT_DE_PASSE" \
  http://127.0.0.1:2333/v4/info

curl -i -H "Authorization: VOTRE_MOT_DE_PASSE" \
  http://127.0.0.1:2333/v4/stats

/version permet de vérifier que le serveur répond. /v4/info et /v4/stats vérifient aussi l'authentification et l'API Lavalink v4. Remplacez le secret d'exemple par votre mot de passe réel ; ne le publiez pas dans un ticket ou une capture d'écran.

Configurez ensuite votre client Lavalink habituel avec l'hôte, le port, le mot de passe et TLS si votre reverse proxy termine HTTPS. La compatibilité exacte dépend des fonctionnalités utilisées par le client et doit être évaluée avec le registre de compatibilité.

Dépannage

Le processus refuse de démarrer

  • Vérifiez que RAVALINK_PASSWORD est défini et comporte au moins 16 caractères.
  • Vérifiez les journaux : journalctl -u ravalink -n 100 --no-pager ou la console du panel / docker compose logs ravalink.
  • Vérifiez que le port est disponible et que l'adresse d'écoute est valide.

Le client obtient une erreur 401

  • Le secret du client doit correspondre exactement à RAVALINK_PASSWORD.
  • Le client doit transmettre Authorization pour REST et WebSocket.
  • Vérifiez les espaces, retours à la ligne et anciennes valeurs de secret.

Le WebSocket ne se connecte pas derrière Nginx

  • Activez HTTP/1.1 et transmettez les en-têtes Upgrade et Connection.
  • Vérifiez le port amont et les timeouts du proxy.
  • Vérifiez que le pare-feu autorise le trafic TCP vers le proxy.

L'egg s'arrête avant le lancement

  • Vérifiez l'accès sortant vers api.github.com et github.com.
  • Vérifiez que le yolk Debian fournit curl, jq et sha256sum.
  • Vérifiez qu'une release publiée contient le binaire de l'architecture et SHA256SUMS.
  • Ne désactivez pas la vérification SHA-256 pour contourner une erreur.

Compatibilité et limites de la RC1

La RC1 valide les portes automatisées de préparation, la compilation et le smoke test API. Cela ne remplace pas les essais réels de lecture dans des guildes Discord, les tests de charge prolongés ni la validation de chaque fournisseur audio et client tiers.

  • Le route planner natif n'est pas disponible : les opérations correspondantes renvoient les réponses documentées dans le registre de compatibilité.
  • Les flux HTTP progressifs ne sont pas seekables après le début de la lecture ; certaines sources/conteneurs nécessitant un accès aléatoire peuvent échouer.
  • La durée des URL génériques peut être inconnue.
  • Les filtres de plugins sans gestionnaire natif sont rejetés explicitement.
  • La validation de lecture vocale Discord en conditions réelles reste à effectuer pendant le cycle RC.

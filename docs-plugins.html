Plugins & extensions

Installer, développer et sécuriser des extensions RavaLink.

Modèle d’extensions

RavaLink est écrit en Rust. Ses extensions ne sont pas des plugins Java : les fichiers .jar conçus pour Lavalink Java et l’API Spring ne sont pas chargeables. Le projet distingue les intégrations natives compilées dans le workspace Rust et les extensions externes exécutées comme processus enfants.

À retenir : l’interface externe est un protocole JSON versionné sur stdin/stdout. Ce n’est ni un ABI de bibliothèque dynamique ni un bac à sable. Un exécutable de plugin s’exécute avec les droits du compte système RavaLink.

Installer une extension externe

  1. Récupérez une distribution de plugin depuis une source que vous connaissez et vérifiez son intégrité.
  2. Créez un sous-dossier dédié dans le répertoire de plugins (par défaut plugins/).
  3. Placez l’exécutable et son manifeste ravalink-plugin.toml dans ce dossier.
  4. Rendez le binaire exécutable et vérifiez que l’utilisateur RavaLink peut le lire et l’exécuter.
  5. Redémarrez le serveur et inspectez les journaux de découverte/initialisation.
mkdir -p plugins/community-source
install -m 0755 ./community-source plugins/community-source/community-source
# Créez plugins/community-source/ravalink-plugin.toml

Exemple de manifeste

name = "community-source"
version = "1.0.0"
description = "Exemple d’intégration communautaire"
capabilities = ["track", "playlist", "search", "source:community"]
identifier_prefix = "community:"
program = "./community-source"
args = ["--stdio"]

[environment]
API_TOKEN = "injecter-un-secret-deploiement"

[config]
region = "eu"

Les chemins d’exécutable relatifs sont résolus depuis le dossier du plugin. Gardez les secrets hors du dépôt et limitez les permissions du fichier ou du mécanisme qui les injecte. Les champs et capacités acceptés doivent correspondre au manifeste pris en charge par la version installée.

Contrat du manifeste

Les champs principaux sont name, version, description, capabilities, identifier_prefix, api_version, program et args. Les tables [config] et [environment] transmettent respectivement la configuration du plugin et les variables explicitement autorisées. Les noms et préfixes doivent être uniques ; les noms intégrés youtube, lavasrc et lavasearch sont réservés. Pour une déclaration directe dans le TOML du serveur, le chemin de program doit être absolu.

Protocole externe v1 — exemple d’échange

Pour chaque identifiant correspondant au préfixe, l’hôte lance le programme, lui transmet une seule requête JSON sur stdin, ferme stdin, lit stdout puis attend la fin du processus. La requête inclut la version du protocole, l’identifiant et la configuration du plugin :

{"protocolVersion":1,"identifier":"community:some-track","config":{"region":"eu"}}

Le programme renvoie exactement une réponse JSON sur stdout. Il peut répondre null si l’identifiant n’est pas géré, ou renvoyer un résultat Lavalink compatible. Exemple minimal d’un résultat de piste :

{
  "loadType": "track",
  "data": {
    "encoded": "...",
    "info": {
      "identifier": "some-track",
      "isSeekable": true,
      "author": "Artist",
      "length": 180000,
      "isStream": false,
      "position": 0,
      "title": "Example track",
      "uri": "https://example.org/track",
      "sourceName": "community"
    },
    "pluginInfo": {
      "streamUrl": "https://cdn.example.org/audio.mp3"
    },
    "userData": {}
  }
}

Les valeurs de loadType prises en charge sont track, playlist et search. Pour la lecture, le résultat doit contenir une piste Lavalink complète et une URL audio HTTP(S) directe et lisible dans pluginInfo.streamUrl. RavaLink applique ses contrôles d’adresse IP publique, de redirection, de format et de décodeur à cette URL.

  • Maximum 4 Mio de sortie stdout par invocation.
  • Maximum deux processus simultanés par extension.
  • Timeout mural de 30 secondes ; un processus expiré est tué.
  • stdout est réservé au JSON ; ne mélangez jamais les logs avec la réponse.
  • Les processus s’exécutent avec le compte système RavaLink, sans sandbox ; seules les variables explicitement configurées sont transmises.

Développer un plugin externe

Le processus est lancé par RavaLink. Il reçoit une requête JSON versionnée sur son entrée standard et renvoie un résultat JSON de chargement de plugin (ou null) sur sa sortie standard. Réservez stdout au protocole : envoyez les logs de diagnostic sur stderr.

  • Traitez chaque message selon la version de protocole annoncée.
  • Validez les champs et refusez proprement les opérations non prises en charge.
  • Retournez des erreurs structurées plutôt que de terminer brutalement le processus.
  • Respectez les limites de temps d’exécution et de taille de réponse imposées par l’hôte.
  • Ne supposez pas l’accès aux objets internes du serveur, au transport vocal Discord, aux décodeurs ou aux routes REST privées.

Le protocole et le contrat de données évoluent avec RavaLink. Avant de publier un plugin, testez-le contre la version cible et consultez le code du contrat :

Exemple exécutable Rust minimal

Ce squelette montre le cycle stdin → désérialisation → réponse JSON. Il renvoie un résultat de recherche vide pour les identifiants community: ; il valide le transport, mais ne fournit pas encore de piste jouable.

# Cargo.toml
[package]
name = "community-source"
version = "1.0.0"
edition = "2021"

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
// src/main.rs
use serde::Deserialize;
use serde_json::json;
use std::io::{self, Read};

#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
struct Request {
    protocol_version: u32,
    identifier: String,
}

fn main() -> Result<(), Box> {
    let mut input = String::new();
    io::stdin().read_to_string(&mut input)?;
    let request: Request = serde_json::from_str(&input)?;

    if request.protocol_version != 1
        || !request.identifier.starts_with("community:")
    {
        println!("null");
        return Ok(());
    }

    let response = json!({
        "loadType": "search",
        "data": { "tracks": [], "pluginInfo": {} }
    });
    println!("{}", serde_json::to_string(&response)?);
    Ok(())
}

Compilez en mode release, copiez le binaire dans le dossier du plugin, puis référencez-le dans le manifeste :

cargo build --release
mkdir -p plugins/community-source/bin
install -m 0755 target/release/community-source plugins/community-source/bin/community-source

Remplacez ce résultat vide par une réponse track, playlist ou search valide. Pour la lecture audio, la piste doit inclure un pluginInfo.streamUrl direct et compatible.

Développer une intégration native Rust

Les intégrations maintenues par le projet sont des crates distinctes du workspace et partagent le contrat ravalink-plugin-api. Pour contribuer :

  1. Forkez le dépôt principal et créez une branche dédiée.
  2. Étudiez une intégration existante (YouTube, LavaSrc ou LavaSearch) et le trait RavaLinkPlugin.
  3. Définissez les capacités et préfixes d’identifiants nécessaires sans élargir inutilement l’API.
  4. Ajoutez des tests unitaires et des tests d’intégration couvrant les erreurs réseau, les données invalides et les réponses vides.
  5. Ajoutez la configuration, la documentation et les tests de compatibilité correspondants.
  6. Lancez les tests du workspace avant d’ouvrir une pull request.
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
Limites actuelles : pas de chargement de JAR Java, pas de chargement dynamique de bibliothèques Rust avec ABI stable, et pas de sandbox de sécurité. Les extensions natives exigent une modification et une recompilation du workspace.

Déployer RavaLink

Installez votre nœud audio Discord en natif sous Linux, avec Docker, ou depuis un panel Pelican / Pterodactyl. Retrouvez ici les étapes, les paramètres, la sécurité et les opérations courantes.

RavaLink est un serveur audio natif écrit en Rust, conçu autour du protocole Lavalink v4. Il fonctionne comme un service séparé de votre bot Discord : le bot lui envoie les requêtes REST et WebSocket, et RavaLink prend en charge le traitement audio et la connexion vocale.

Statut de la version : v1.0.0-rc.1 est une release candidate destinée aux tests. Elle n'est pas déclarée stable et ne doit pas être considérée comme un remplacement de production entièrement validé. Consultez le registre de compatibilité avant un déploiement critique.

Avant de commencer

  • Un hôte Linux 64 bits. Les binaires publiés ciblent x86_64 / amd64 et aarch64 / arm64.
  • Un port TCP disponible pour l'API HTTP et le WebSocket (2333 par défaut).
  • Un mot de passe unique d'au moins 16 caractères. Générez-en un aléatoire ; n'utilisez jamais le mot de passe d'exemple.
  • Un accès sortant à Internet pour récupérer les releases et les sources audio. Le trafic vocal Discord est également initié par le nœud.

Docker Compose est nécessaire uniquement pour le parcours Docker. Pour Pelican/Pterodactyl, vous devez pouvoir importer un egg et créer un serveur dans le panel.

Architecture : utilisez le binaire correspondant à uname -m. Un binaire ARM64 ne fonctionnera pas sur un hôte x86_64, et inversement.

Choisir une installation

Contrôle maximalLinux natif

Pour un VPS ou serveur dédié. Binaire autonome, service systemd, configuration TOML et mises à jour maîtrisées.

Environnement isoléDocker

1. Installation Linux native

Le binaire RavaLink est autonome : aucun runtime Java, JVM, Gradle ou Lavaplayer n'est requis. Cette procédure installe la release candidate v1.0.0-rc.1. Pour une version ultérieure, remplacez simplement la valeur de VERSION.

Télécharger et installer le binaire

Prérequis : curl, sha256sum, openssl et les outils systemd. Sélectionnez automatiquement l'asset adapté à l'architecture, puis vérifiez son empreinte avant installation :

VERSION="v1.0.0-rc.1"
case "$(uname -m)" in
  x86_64|amd64) ASSET="ravalink-linux-x86_64" ;;
  aarch64|arm64) ASSET="ravalink-linux-aarch64" ;;
  *) echo "Architecture non prise en charge"; exit 1 ;;
esac

BASE="https://github.com/Ravalink-Project/Ravalink/releases/download/$VERSION"
mkdir -p /tmp/ravalink-install
cd /tmp/ravalink-install
curl -fL "$BASE/$ASSET" -o "$ASSET"
curl -fL "$BASE/SHA256SUMS" -o SHA256SUMS
grep "  $ASSET$" SHA256SUMS | sha256sum -c -

sudo install -d -m 0755 /opt/ravalink/bin /etc/ravalink
sudo install -m 0755 "$ASSET" /opt/ravalink/bin/ravalink
sudo curl -fL "https://raw.githubusercontent.com/Ravalink-Project/Ravalink/v1.0.0-rc.1/config/ravalink.example.toml" \
  -o /etc/ravalink/ravalink.toml

Le fichier SHA256SUMS est fourni avec la release et couvre les deux binaires Linux. Ne lancez pas un binaire dont la vérification échoue.

Créer un compte système et un service systemd

Exécutez RavaLink sous un compte dédié, sans privilèges root :

sudo useradd --system --home-dir /var/lib/ravalink \
  --create-home --shell /usr/sbin/nologin ravalink
sudo chown -R ravalink:ravalink /var/lib/ravalink

sudo sh -c 'printf "RAVALINK_PASSWORD=%s\\n" "$(openssl rand -hex 32)" > /etc/ravalink/ravalink.env'
sudo chmod 600 /etc/ravalink/ravalink.env

Créez /etc/systemd/system/ravalink.service :

[Unit]
Description=RavaLink native audio node
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=ravalink
Group=ravalink
WorkingDirectory=/var/lib/ravalink
EnvironmentFile=/etc/ravalink/ravalink.env
Environment=RAVALINK_CONFIG=/etc/ravalink/ravalink.toml
Environment=RAVALINK_ADDRESS=127.0.0.1
Environment=RAVALINK_PORT=2333
Environment=RAVALINK_LOG_LEVEL=info
ExecStart=/opt/ravalink/bin/ravalink
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/ravalink

[Install]
WantedBy=multi-user.target

Chargez le service et démarrez-le :

sudo systemctl daemon-reload
sudo systemctl enable --now ravalink
sudo systemctl status ravalink
sudo journalctl -u ravalink -f
Adresse d'écoute : l'exemple systemd écoute sur 127.0.0.1, adapté à un reverse proxy installé sur le même hôte. Si le bot se connecte depuis une autre machine, configurez une adresse joignable (souvent 0.0.0.0) et limitez l'accès avec un pare-feu ou un réseau privé. N'exposez pas le port sans authentification ni contrôle réseau.

Mettre à jour le binaire natif

Conservez votre TOML et votre fichier d'environnement. Téléchargez la nouvelle release, vérifiez SHA256SUMS comme à l'installation, remplacez le binaire, puis redémarrez :

sudo systemctl stop ravalink
# Après téléchargement et vérification du nouvel asset :
sudo install -m 0755 ./ravalink-linux-x86_64 /opt/ravalink/bin/ravalink
sudo systemctl start ravalink
sudo journalctl -u ravalink -n 80 --no-pager

Utilisez l'asset ARM64 sur une machine aarch64. Vérifiez les notes de version et les changements de configuration avant chaque mise à jour.

2. Déploiement Docker

Le dépôt fournit un Dockerfile multi-stage et un fichier compose.yml. L'image finale contient le binaire Rust et les certificats CA ; le processus tourne avec l'utilisateur non privilégié ravalink.

À savoir : le Compose fourni construit l'image depuis le code présent dans le dépôt (build: .). Le tag local ghcr.io/ravalink-project/ravalink:dev ne signifie pas qu'une image préconstruite de production est publiée sur GHCR.

Docker Compose (recommandé)

Installez Docker Engine et le plugin Docker Compose, puis clonez le dépôt :

git clone https://github.com/Ravalink-Project/Ravalink.git
cd Ravalink
cp config/ravalink.example.toml ravalink.toml

printf 'RAVALINK_PASSWORD=%s\\n' "$(openssl rand -hex 32)" > .env
chmod 600 .env

docker compose up -d --build
docker compose ps
docker compose logs -f ravalink

Le fichier Compose publie par défaut le port du conteneur uniquement sur 127.0.0.1:2333 de l'hôte. La configuration TOML est montée en lecture seule dans le conteneur à /etc/ravalink/ravalink.toml. Les variables d'environnement remplacent les valeurs du fichier.

Pour arrêter le service sans supprimer la configuration :

docker compose down

Pour reconstruire après avoir récupéré une nouvelle version du dépôt :

git pull --ff-only
docker compose up -d --build

Build et lancement manuels

docker build -t ravalink:local .
docker run -d --name ravalink --restart unless-stopped \
  -p 127.0.0.1:2333:2333 \
  -e RAVALINK_PASSWORD="$(openssl rand -hex 32)" \
  -v "$PWD/ravalink.toml:/etc/ravalink/ravalink.toml:ro" \
  ravalink:local

Pour rendre le service accessible à distance, modifiez volontairement le binding réseau et appliquez les règles de pare-feu décrites dans la section Réseau et sécurité. Ne montez pas le socket Docker dans le conteneur RavaLink.

3. Pelican et Pterodactyl

L'équipe publie un egg compatible avec les deux panels. Il utilise le yolk Debian, installe un script de démarrage, détecte l'architecture et récupère le binaire depuis la dernière GitHub Release publiée.

Dépôt officiel des eggsTélécharger egg-ravalink.json

Importer l'egg

  1. Connectez-vous au panel avec un compte administrateur.
  2. Ouvrez Nests / Eggs (Pelican : la rubrique équivalente de gestion des eggs), puis importez le fichier egg-ravalink.json.
  3. Associez l'egg au Nest de votre choix. Le fichier déclare l'image Docker ghcr.io/pterodactyl/yolks:debian.
  4. Enregistrez l'egg et vérifiez que son script d'installation a été exécuté lors de la création du serveur.

Créer et configurer le serveur

  1. Créez un nouveau serveur et sélectionnez le Nest puis l'egg RavaLink.
  2. Allouez un port TCP au serveur. Le port par défaut de RavaLink est 2333 ; le panel doit transmettre ce port dans RAVALINK_PORT.
  3. Dans les variables de démarrage, remplacez impérativement RAVALINK_PASSWORD par un secret aléatoire d'au moins 16 caractères. La valeur par défaut est volontairement invalide.
  4. Vérifiez l'image Debian, l'allocation et les limites de ressources, puis démarrez le serveur.
  5. Consultez la console : le script indique la release détectée, l'architecture et le résultat de la vérification SHA-256 avant de lancer RavaLink.

Le script configure par défaut l'écoute sur 0.0.0.0 et le port 2333 si les variables ne sont pas définies. Le port alloué dans le panel doit correspondre à RAVALINK_PORT.

Mises à jour et sélection de version

À chaque démarrage, le script consulte l'API GitHub Releases, sélectionne la release publiée la plus récente (les préversions sont incluses, les drafts exclues), télécharge le binaire correspondant à l'architecture et le vérifie avec SHA256SUMS. Si la même version est déjà installée et que son empreinte est valide, le téléchargement est évité.

Important : l'egg suit automatiquement la dernière release publiée. Il ne propose pas de variable de version pour épingler une release. Un redémarrage peut donc installer une nouvelle RC ou une version stable dès qu'elle est publiée. Vérifiez la page Releases avant de redémarrer un serveur critique.

En cas d'indisponibilité de GitHub, de binaire manquant ou de checksum invalide, le script arrête le démarrage au lieu d'exécuter silencieusement un ancien binaire non vérifié.

Réseau et sécurité

  • TCP 2333 : API REST Lavalink v4 et WebSocket. N'ouvrez que ce port si vos clients doivent joindre le nœud.
  • Sortie réseau : nécessaire pour GitHub Releases, les fournisseurs audio et les connexions vocales Discord.
  • Authentification : toutes les requêtes REST et la connexion WebSocket doivent fournir le secret dans l'en-tête Authorization.
  • TLS : placez un reverse proxy HTTPS/WSS devant RavaLink lorsque le trafic traverse Internet. Le proxy doit transmettre les connexions WebSocket (Upgrade).
  • Prometheus : les métriques sont désactivées par défaut. L'endpoint n'ajoute pas d'authentification ; ne le rendez pas public sans contrôle d'accès.
  • Privilèges : utilisez un utilisateur système non-root pour l'installation native ; le conteneur officiel s'exécute sans privilèges root.

Exemple Nginx (reverse proxy WebSocket)

Remplacez audio.example.com par votre nom de domaine et configurez votre certificat TLS dans le bloc serveur :

server {
    listen 443 ssl http2;
    server_name audio.example.com;

    # ssl_certificate et ssl_certificate_key à configurer

    location / {
        proxy_pass http://127.0.0.1:2333;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}

Ne retirez pas l'authentification RavaLink au niveau du proxy. Si vous utilisez un proxy TCP ou un tunnel, vérifiez qu'il préserve les connexions WebSocket et les en-têtes HTTP.

Vérifier le fonctionnement

Depuis la machine qui héberge le nœud, vérifiez d'abord que le processus écoute sur le bon port. Les routes protégées nécessitent l'en-tête Authorization.

curl -i http://127.0.0.1:2333/version

# Exemple pour une route authentifiée :
curl -i -H "Authorization: VOTRE_MOT_DE_PASSE" \
  http://127.0.0.1:2333/v4/info

curl -i -H "Authorization: VOTRE_MOT_DE_PASSE" \
  http://127.0.0.1:2333/v4/stats

/version permet de vérifier que le serveur répond. /v4/info et /v4/stats vérifient aussi l'authentification et l'API Lavalink v4. Remplacez le secret d'exemple par votre mot de passe réel ; ne le publiez pas dans un ticket ou une capture d'écran.

Configurez ensuite votre client Lavalink habituel avec l'hôte, le port, le mot de passe et TLS si votre reverse proxy termine HTTPS. La compatibilité exacte dépend des fonctionnalités utilisées par le client et doit être évaluée avec le registre de compatibilité.

Dépannage

Le processus refuse de démarrer

  • Vérifiez que RAVALINK_PASSWORD est défini et comporte au moins 16 caractères.
  • Vérifiez les journaux : journalctl -u ravalink -n 100 --no-pager ou la console du panel / docker compose logs ravalink.
  • Vérifiez que le port est disponible et que l'adresse d'écoute est valide.

Le client obtient une erreur 401

  • Le secret du client doit correspondre exactement à RAVALINK_PASSWORD.
  • Le client doit transmettre Authorization pour REST et WebSocket.
  • Vérifiez les espaces, retours à la ligne et anciennes valeurs de secret.

Le WebSocket ne se connecte pas derrière Nginx

  • Activez HTTP/1.1 et transmettez les en-têtes Upgrade et Connection.
  • Vérifiez le port amont et les timeouts du proxy.
  • Vérifiez que le pare-feu autorise le trafic TCP vers le proxy.

L'egg s'arrête avant le lancement

  • Vérifiez l'accès sortant vers api.github.com et github.com.
  • Vérifiez que le yolk Debian fournit curl, jq et sha256sum.
  • Vérifiez qu'une release publiée contient le binaire de l'architecture et SHA256SUMS.
  • Ne désactivez pas la vérification SHA-256 pour contourner une erreur.

Compatibilité et limites de la RC1

La RC1 valide les portes automatisées de préparation, la compilation et le smoke test API. Cela ne remplace pas les essais réels de lecture dans des guildes Discord, les tests de charge prolongés ni la validation de chaque fournisseur audio et client tiers.

  • Le route planner natif n'est pas disponible : les opérations correspondantes renvoient les réponses documentées dans le registre de compatibilité.
  • Les flux HTTP progressifs ne sont pas seekables après le début de la lecture ; certaines sources/conteneurs nécessitant un accès aléatoire peuvent échouer.
  • La durée des URL génériques peut être inconnue.
  • Les filtres de plugins sans gestionnaire natif sont rejetés explicitement.
  • La validation de lecture vocale Discord en conditions réelles reste à effectuer pendant le cycle RC.
